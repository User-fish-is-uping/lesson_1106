# 基于 K210 人脸检测的工位占用提示器：三小时双人开发计划

## 1. 推荐结论与边界

选题：基于 K210 人脸检测与时序确认的工位占用提示器。

演示过程：无人时绿灯；人正对摄像头、持续检测约 1 秒后红灯；短暂转头或遮挡不立即释放；持续约 3 秒未检测到人脸后恢复绿灯。屏幕显示检测框、状态和本次占用时长，串口输出状态变化。

这是“基于可见人脸判断”的工位占用原型。背对摄像头、长期遮脸会误判；不能宣称能够可靠判断所有在座情况。不识别人是谁，不做身份门禁，不从人数推算进出人数。时间是初始调参值，最终按板端实测调整。

已知硬件：实物丝印 Yahboom YB-DKA01 VER:1.1；用户确认有摄像头和屏幕。摄像头型号、固件、IDE、配套例程和模型版本尚未确认。说明书图片里的板卡版本与实物不完全相同，不能直接照搬引脚。

三小时目标是可演示原型，不是完成全部课程材料。能否按时完成，首先取决于匹配的课程人脸检测例程和模型能否跑通。

《第二节》第 5 页介绍板载 RGB；第 14、17 页强调先做 FPIOA 引脚映射。物理引脚、GPIO 编号、有效电平以本板对应资料和可运行例程为准。

## 3. 先理解整个流程

电脑修改代码 → 编译并烧录 C 工程，或用配套 IDE 运行 MicroPython → 板载摄像头采图 → KPU 使用已有模型检测人脸 → 状态逻辑过滤短时波动 → LCD 和 RGB 显示结果 → 串口日志反馈给 Codex 排查。

编译路线和 Python 路线只选已能运行的一条。优先保留现有 C SDK 工作流；只有配套 MicroPython 固件、人脸脚本及模型已齐全时才选 Python。标准电脑 Python 不能直接运行 K210 的 sensor、lcd、KPU 等板端模块。不要为切换语言反复覆盖固件。

不需要另购传感器，不需要云端推理、联网、数据库或重新训练。没有模型文件时，云端不能凭空生成一个已适配板子的模型。

## 4. 两个人和两个 Codex 怎么分工

你：需求与逻辑负责人。与云端 Codex 确定状态行为、测试表、版本说明和汇报；把代码交给同学；记录测试结果、拍摄演示。

同学：硬件与集成负责人。与桌面 Codex 检查本机资料、SDK、IDE、串口、摄像头和模型；运行最小例程；把业务逻辑接入现有循环，完成上板测试。

云端 Codex：编写独立业务逻辑和有意义的离线测试；依据实际工程写适配代码；解释报错；整理说明和汇报。不能直接连接同学电脑上的 USB，也不能把离线测试当作板端验证。

桌面 Codex：检查授权的本地项目；确认工具链与模型加载方式；修改本地适配层；运行可用编译和日志命令。IDE 点击、插拔线缆、按键、摄像头摆位由同学执行，除非本地工具确实支持自动操作。

协作规则：集成版本由同学维护；云端主要交付逻辑模块和测试。共享仓库时明确各自修改的文件、先同步再集成；来不及配置 Git 时直接传小文件并标版本，禁止两边同时覆盖同一入口文件。两个会话不会自动共享聊天或本地文件。

| 40–60 分钟 | 单独验证 RGB 红、绿、熄灭；记录引脚和有效电平 | 完成进入、离开、计时的边界检查，给出接口 | 灯能独立控制；业务逻辑有可复现结果 |

| 125–150 分钟 | 测重启与脱离 IDE 运行；整理模型和程序位置 | 整理复现步骤、已知限制、简短演示稿 | 重启后能按文档恢复运行；脱机能力以实测为准 |

前 40 分钟的门槛很重要：如果人脸例程没有跑通，优先诊断摄像头驱动、模型与固件/SDK 兼容、烧录地址、串口占用；此时只继续开发可离线验证的逻辑，不叠加新硬件功能。

若仍缺少配套模型或固件，使用课程原始资料或向助教索取匹配版本；不得把随机模型、占位文件或模拟检测结果包装成实物 AI 成功。只在老师明确接受传统颜色识别作为 AI 功能时，才转用颜色方案作为课程题目。

## 6. 最小功能与接口约定

必须：真实模型推理、屏幕画面与框、无人/有人状态、进入确认、离开保持、红绿灯反馈、串口变化日志。

基础功能稳定后再加：本次占用秒数、启动检查页。按钮复位、蜂鸣器、Wi-Fi、网页、自训模型本轮不安排。

检测适配层输入：当前帧检测框，按已有例程正确取得坐标与置信度；若启用 ROI，只保留目标工位区域内的有效框。初版只做单工位，不承诺多人跟踪。

业务层输入：单调时间毫秒值、是否检测到有效人脸。输出：状态、是否切换、占用时长。C 和 MicroPython 的时间回绕分别使用适合的差值实现。

建议状态：FREE → ENTER_PENDING → OCCUPIED → EXIT_PENDING → FREE。进入确认中丢失目标则回到 FREE；离开确认中再次检测到目标则回到 OCCUPIED 并保留计时；只有持续未检测满足离开阈值才释放。初始化或推理异常显示 ERROR/UNKNOWN，不直接显示“空闲”。

绿灯：空闲；红灯：已占用；待确认可保持前一稳定灯色，屏幕显示 PENDING；异常显示错误文字。黄色提示作为可选项，不为它扩大 GPIO 调试范围。

屏幕初版使用 FREE、OCCUPIED、PENDING、ERROR 和秒数，避免额外加载中文字库。以非阻塞计时实现 1 秒/3 秒规则，不能 sleep 数秒导致摄像头停止刷新。

建议文件拆分随工程语言确定：状态逻辑、硬件适配、入口、离线测试、运行说明。拿到真实例程后再确定 API 和文件名，不预设不存在的库函数。

## 7. 实物验收表

| 操作 | 预期 | 记录 |
|---|---|---|
| 启动且画面无人 | 初始化完成后显示 FREE，绿灯 | 启动耗时、有无错误 |
| 人脸连续出现超过确认时间 | 标框，OCCUPIED，红灯 | 实测切换延迟 |
| 人脸只闪现不到确认时间 | 不进入稳定占用 | 是否误触发 |
| 占用时短暂遮挡约 1 秒 | 保持占用与计时 | 灯是否闪烁 |
| 人离开超过释放时间 | FREE，绿灯，结束本次计时 | 实测释放延迟 |
| 释放倒计时内重新出现 | 取消释放，保留原占用计时 | 是否错误清零 |
| 完整进入离开重复 10 次 | 逐次记录结果，目标至少 9 次符合规则 | 成功数/10，不能预填 |
| 连续运行 5 分钟 | 无崩溃、无持续卡死 | 实际运行时长 |
| 断电重启一次 | 按已验证步骤恢复运行 | 是否自动启动、所需人工操作 |

“至少 9/10”是计划目标，不是模型准确率结论。正脸、正常室内光照和固定距离是本轮演示条件。背脸、长期遮挡、照片或手机人脸可能造成误判，不宣称活体检测、身份识别或生产级座位监测能力。

## 8. 常见故障和反馈方式

看不到串口：确认 Type-C 数据线、供电开关、CH340 驱动和实际端口，关闭占用串口的其他软件。

有串口无画面：断电后检查排线方向和锁扣；确认摄像头型号、板卡版本及课程驱动匹配，避免带电插拔排线。

模型加载失败：记录文件名、大小、固件/SDK 版本、加载路径或烧录地址、完整错误。优先恢复课程已配对文件，不混搭不同版本 kmodel。

灯颜色错误：先跑对应板版本的独立 RGB 例程，核实物理 IO、FPIOA 映射、有效电平与外设冲突；不能从颜色开题 PPT 直接推定本板接法。

框正常但灯频繁跳：检查时序逻辑是否每帧错误重置、计时来源是否正确、是否用阻塞延时。

反馈模板：版本号；C/Python 路线；固件/SDK 版本；实际运行命令或 IDE 操作；完整报错文字；期望行为；实际行为；刚改了什么。优先贴日志原文，辅以实物照片。
