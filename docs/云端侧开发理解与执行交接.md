## 1. 请先核对我的总体理解

我们共同开发《基于 K210 的双向客流统计与语音迎宾系统》，采用课程现有的 person 检测模型，不再沿用此前云端提出的工位占用方案。系统流程是：摄像头与 KPU 输出人员框 → 桌面适配为统一帧 → 云端 core 判断完整通行 → core 更新计数并生成唯一事件 → 事件进入语音队列 → 桌面播放器播放 → LCD、串口显示实际状态。

首版仅面向单人依次通过的演示场景。多人、截断、轨迹跳变等片段保守处理，不承诺多人跟踪，不用人脸检测替代人员检测，不声称身份识别或活体识别。

三小时是首轮预算。优先顺序为：公开头文件与接口审阅 → core 和主机测试，同时桌面跑视觉独立链路 → 视觉计数集成 → 音频队列与真实播放。即使音频硬件暂缺，core 仍可实现与测试；这不代表完整迎宾实物已经完成。

当前对本地工具链、模型标签及课程源码的认识来自桌面侧记录。云端没有复核你本机目录，没有连接板卡，也没有取得真实检测日志。

## 3. 已确认、我会直接遵守的规则

### 3.1 可移植性和时间

- C99 子集，无堆分配、SDK 头文件、GPIO、文件系统、睡眠或真实音频调用。
- 实例由调用方持有，无全局单例；core 只从单线程主循环调用，中断不得直接调用。
- `sequence_id`、`event_id`、`now_ms` 为 `uint64_t`；毫秒时间由桌面传入，共用单调时钟。
- 每次上电重新初始化；清零计数不重置事件编号。core 不读墙钟，不自行调用板端计时函数。
- 主机目标显式 C99；桌面 gnu11 工程能否编译仍由实际交叉编译验证。

### 3.2 检测输入

- 使用 person 模型，课程标签零基索引 14；桌面显式筛选 person 与 `score > 0.50`，core 对可配置阈值也使用严格大于。
- 原始框对应 320×240；先在浮点阶段裁剪 x 到 [0,319]、y 到 [0,239]，再除以 319.0f、239.0f；320×256 不是归一化分母。
- 框为归一化坐标，默认底边中心；X 主轴取中心 x，Y 主轴取底边 y。
- 显示镜像、旋转和相机方向由桌面适配，使线与框一致，core 不再镜像。
- 有效空画面是 `valid=true, person_count=0`，采集/推理故障是 `valid=false`。
- 容量为 10；`truncated` 表示列表完整性不确定，按歧义处理。桌面必须写数组前检查容量。
- 一次真实推理帧只调用一次 `greeter_update`；一次 update 最多一个通行事件。

### 3.3 通行语义

- A 外侧：`p < line_a-hysteresis`；B 外侧：`p > line_b+hysteresis`。
- 中间证据：`line_a+hysteresis <= p <= line_b-hysteresis`；其余为缓冲带。
- 先在一侧稳定建立起点，之后至少有一帧有效、关联合理的中间证据，最后另一外侧稳定，才能计数。
- 直接 A/B 跳变且无中间证据：不计数，旧候选清除，当前帧仅开始建立新起点。
- 停留、抖动、半程折返不计数。完整 A→B 后，B 是新的稳定起点，允许完整返回 A 再产生反向事件。
- 短时空检测仅在宽限、关联和超时条件均满足时保留候选；长时丢失、无效帧、时间倒退、明显轨迹跳变清候选。
- 多人或截断进入歧义；恢复单人后重新建立稳定外侧，不能接续之前的半程轨迹。
- A→B 默认 ENTER，反向 EXIT；`reverse_direction` 只反转事件含义，不改变坐标或历史计数。
- core 负责累计计数，firmware 只读取快照，禁止再重复加计数。音频异常不回滚通行计数。

### 3.4 语音与控制

- 固定容量 4，保存事件，不保存 WAV 数据。ENTER/EXIT 对应 `0:/welcome.wav`、`0:/goodbye.wav`。
- 保持 FIFO、按 ID 防重；满时保留旧项，丢新项并累计原因。
- 初始最大等待 5000 ms；每项最多两次真实启动尝试，BUSY 不消耗次数。
- STARTED 才消费队首；首次 FAILED 保留到之后一次服务重试；第二次 FAILED 丢弃并记录。
- STARTED 后异步出错只记录，不重排已消费事件。
- 静音时清空待播，期间不入队，恢复不补播。当前一句允许播完。
- 清零、实际改变方向时清候选与待播；切换到相同方向不视为实际改变。
- 清队列保留去重水位、累计错误及事件编号；这些控制先于下一帧与下一次调度执行。
- 播放器状态、DMA/SD/I2S、异步完成与资源回收归桌面；core 不感知通道号。

## 4. 还需补齐的边界：提出默认值，请在头文件冻结时核对

以下是对 v0.2 未完全明确处的建议，不把它们描述成已由桌面确认。可独立开始头文件草案和测试，不需要等待板卡或录音。

| 问题 | 云端建议默认行为 | 原因 |
|---|---|---|
| 同一或倒退帧号 | 重复/倒退序号不处理、不产事件、不推进逻辑时间；返回可区分诊断。重启必须重新 init | 避免旧日志破坏当前轨迹；序号恢复策略须明确 |
| 相同时间戳的新帧 | 允许处理，但不累计稳定时长；关联只使用配置基础容差 | 帧率或计时精度可能导致同毫秒 |
| 时间倒退 | 对序号有效的新帧，清轨迹并报告；该帧不作为新起点，后续有效帧重新建立；更新后的时间基准以恢复规则文档为准 | 避免错误恢复时沿用轨迹；公开说明并测出精确行为 |
| 稳定时间 | 端点要求连续有效单人观测；进入缓冲带、中间、空帧或异常会打断该端点稳定计时，即便短空帧仍保留通行候选 | “候选保留”与“端点连续稳定”应分开 |
| 边界等号 | 稳定满足 `elapsed >= stable_ms`；丢失仅 `elapsed > grace_ms` 失效；穿越在 `elapsed > timeout_ms` 失效；音频等待 `age >= max_wait_ms` 过期 | 避免双方对阈值恰好相等时理解不同 |
| 候选穿越超时起点 | 起点稳定后，首次离开原外侧时开始计穿越超时；原侧长期站立不消耗穿越时限；未完成折返并在原侧重新稳定后清中间证据和旧计时 | 防止“站久了就无法出发”和旧证据误用 |
| 关联算法 | 比较连续有效单人参考点的二维归一化欧氏距离，允许距离=`base_tolerance + max_speed_per_s × dt_seconds`；与最后一次检测点比较，不与空帧比较；dt 还受丢失宽限限制 | 公开量纲，避免仅检查 X 导致明显换人未被发现 |
| 初始关联参数 | 参数显式可配；测试用明确值，默认建议值会写在头文件并标未实板标定 | 不能把主机通过当作现场可用 |
| 非法框/输入 | `person_count>10` 在访问数组前拒绝；NaN/Inf、越界、退化框、非法分数按输入异常清候选，不自行猜测坐标；合法低置信框可过滤 | 限定桌面与 core 的数据责任，避免越界 |
| 配置合法性 | 所有浮点有限；阈值 [0,1]；0<line_a<line_b<1；hysteresis>=0，外侧可用，中间严格有正宽度；稳定时间、宽限、穿越时限关系与关联参数写成明确条件 | 拒绝虽然能初始化但实际不可工作的组合 |
| 去重水位 | 消费、丢弃、静音、满队列见过的合法 ID 都提升水位；之后 `id<=watermark` 视为旧/重复，不重入队 | 按有序事件流实现固定内存防重 |
| 队列时间来源 | 过期从事件 `timestamp_ms` 计算；未来时间戳或倒退的服务时间明确拒绝并记录，不做无符号减法回绕 | 检测和音频共用时钟才能正确计算延迟 |
| 服务重试接口 | 队首查看与启动结果提交分离，提交时带 event_id 校验；一次主循环服务最多启动一个队首，不在 FAILED 后立刻循环重试 | 避免错消费、忙循环和连续重试 |
| 错误分类 | 区分启动失败次数、最终失败丢弃、异步失败、满队列、过期、静音丢弃、清空、重复；不要统一当播放失败 | 便于实测解释语音漏播原因 |
| 整数溢出 | 计数饱和并诊断，事件 ID 用尽后拒绝产生可重复 ID；时间/序号溢出要求重建实例，不静默回绕 | 确保公开接口没有未定义的编号行为 |

其中帧序号恢复、稳定计时打断、穿越超时起点、二维关联参数、音频过期等号和去重水位最值得先核对。若桌面有现成调用约束，请指出具体行和期望行为；云端据此更新草案。调整时不自行改写已确认的 v0.2 规则。

## 5. 我的具体开发顺序与交付

### D0：核实工作区并整理协作入口

检查远端 HEAD、文件和实际权限，保留已有改动；若桌面已上传启动包，先对齐远端，不覆盖。使用现有 checkout，不创建额外 worktree。导入缺失的协作文件，标明旧方案不再生效；建立 `cloud/core`。不将课程 SDK、工具链、临时上传附件或生成构建目录提交进仓库。

交付：实际分支/提交或权限阻塞说明，统一文档入口。只报告已经完成的 Git 操作。

### D1：先交公开头文件草案

实现 `core/greeter.h`、`core/audio_queue.h`，定义配置、初始化与校验结果、输入框/帧、状态/错误枚举、事件、快照、调用方持有状态和队列结构。写明函数的参数、返回值、失败时是否改状态、输出对象何时有效以及时间规则。

greeter 将有初始化、逐帧更新、读取快照、清零、切换方向接口；队列将有初始化、入队、清理过期、看队首、提交启动结果、静音/清空及统计查询接口。具体 C 签名以草案为准，不让桌面先凭函数名猜调用方式。

同时给出配置校验条件、建议初始参数、主循环调用伪代码和边界规则。尽早交完整 SHA，桌面审阅后冻结；此时“头文件能编译”不表示逻辑已实现。

### D2：实现与确定性测试

实现状态机及对称的 A→B/B→A 测试，检查真实事件类型、时间、ID、计数和异常后的恢复，不只检查返回成功。

覆盖：初见中间、正常穿越、原地停留、缓冲带与线边界、半程折返、完成后立即反向、直接跨区跳变、有中间证据后的不合理跳变、短空帧、宽限边界、长丢失、无效帧、多人、截断、重复/旧帧、相同时间、时间倒退、清零与方向切换、X/Y 主轴、配置和非法数据。

实现音频队列并测试：FIFO、ID 去重、成功消费、BUSY 保留、一次失败后重试、二次失败丢弃、满队列、过期及边界、静音进入/退出、清队列水位保留、异步失败不重排、启动结果 ID 不匹配。

主机入口采用：

```sh
cmake -S . -B build/host
cmake --build build/host
ctest --test-dir build/host --output-on-failure
```

命令需要在代码实现后真实执行，记录测试数量与结果。至少开启适当编译警告；若主机支持，可运行地址/未定义行为检查以定位数组和整数问题。主机测试不链接板端 SDK，也不需要实际 kmodel。

交付：实现、主机测试、实际运行结果、接口提交号、最小接入示例、已知限制。桌面用相同源码交叉编译，不复制改写第二套逻辑。

### D3：配合桌面视觉计数集成

桌面将真实帧交给 core，读取快照显示并记录 JSONL。若交叉编译失败，请发编译命令、错误全文和对应 SHA；云端修 core 可移植性。若板端误计，请发原始帧与人工动作说明，云端先复现再修复，保持原有测试。

此阶段不为了修逻辑去改 DMA、摄像头或显示方向；这些由桌面修。core 参数需要改时记录配置版本，避免“源码相同但阈值不同”无法复现。

### D4：日志回放与后续音频验证

实现 `tools/host/` 日志回放，解析约定 frame JSONL，复用同一份 C core，不另写 Python 通行算法。解析时报告行号；明确如何处理非 frame 记录、坏行、缺字段及数据范围。先交清楚标注 synthetic 的示例和测试，再接真实日志。

桌面提供真实数据后，云端保留原始输入与人工标注，分析漏计、重复和错方向；没有真实数据时不输出虚构正确率。若时间允许再做单线基线对照，基线结果与正式状态机结果分别报告。

音频方面只模拟队列行为，真实 WAV、启动状态包装、资源释放、播放时持续推理由桌面实测。云端按日志核对事件与排队顺序。

### D5：交付与回归

每轮留下：分支和完整 SHA、接口版本、变更文件、命令、通过/失败/未跑项、数据来源、已知限制、桌面下一步。编译生成目录不交源码库；发布固件与 SHA256 由桌面维护。

发现 bug 时先保留可复现输入，补回归案例，再修实现。若公开接口需要变化，先给差异说明，由桌面同步调用方后再冻结新版本，禁止静默改字段。

## 6. 桌面现在可以并行做什么

1. 验证仓库访问，上传缺失启动包并回传分支/SHA，避免双方重复初始化。
2. 准备视觉独立版本，确认编译与实板状态；不等待 core 实现才检查摄像头。
3. 核实真实框坐标、person 过滤、容量安全和镜像，采集帧间隔及少量 JSONL。
4. 审阅云端公开头文件，指出调用方内存、C 类型、日志或编译约束。
5. TF/WAV 未齐时先继续视觉与计数；资料齐后独立验证音频，再审查并发与 DMA 分配。

云端希望后续真实日志同时附：固件源码 SHA、接口/配置版本、完整参数、相机摆位和方向、框坐标是否归一化、帧间隔、人工动作时间窗，以及是否启用语音。原始日志应保留，不只截取已经发生事件的几行。
